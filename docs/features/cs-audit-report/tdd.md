### Five defects the tests caught during implementation

Each is a bug I wrote and the suite refused:

1. **The entry's own uid counted as an asset reference.** Broadening the reference scan to accept any `{uid}` object meant an entry marked a same-uid asset as used merely by existing, so the asset was never flagged. Caught by `TC_AR_016 (negative)`. Fixed by skipping record-level metadata keys.
2. **Module presence judged two different ways.** Content types by data, entries by files. Caught by `TC_AR_012 (positive)`. Now uniform: presence means *a data file for that module exists*.
3. **Asset-URL matching required an 8-character uid**, so short uids in URLs were missed. Caught by four reference-detection cases.
4. **`loadAuditItems` read its request back out of the slice** instead of taking it explicitly, which hid the page reset behind reducer ordering. Caught by the filter and search cases; the explicit form is also the better contract.
5. **The re-run toast was raised by the thunk, not the click** — invisible to any caller that mocks thunks, and it tied the acknowledgement to work starting rather than to the interaction. Caught by `TC_AR_140`.

### A deviation from the TRD worth naming

[trd.md TC-2](./trd.md) says the client re-derives impact "using the same functions the server uses". In a repository where `api/` and `ui/` are separate packages with no shared module, that is not literally achievable, so `ui/v3/utils/auditDecisions.ts` is a **parallel implementation** of the api service, held to equivalent tests on both sides. The file says so at the top. If the two ever drift, the impact panel and the footer will disagree with the endpoint and the user has no way to know which to believe — so this is the pair to keep in step, or to extract into a shared package when one exists.

The client's `countExcluded` also differs in *method*, necessarily: the client holds one page, so it cannot enumerate the flagged set. It counts arithmetically from the check counts adjusted by overrides. Same answers, different route — and worth knowing when reading the two side by side.

### Deviations from the design — deliberate, not drift

- **D-1 — the excluded strip's tail is one text node** where the design bolds **not**. Carried over from Phase 2 and *reconsidered here*: the plan was to restore the emphasis with CSS on the existing span, but the emphasis falls mid-phrase, so any element boundary splits the sentence and a screen reader announces it in fragments. TC_AR_067/068 also broke on the attempt. The strip is already the loudest element on an excluded card — danger colour, danger background, an ✕ — so the lost bold costs very little and a legible sentence costs nothing. **Kept as a deviation.**
- **D-2 — a real `<table>`** where the design uses `display: grid`. Grid on a table strips row/column roles in Chrome and Firefox; six columns of tabular data with a header need those roles.
- **D-3 — three column widths differ** (72→96, 60→78, 96→128). The design's values are correct for the design's own content and clip against real data (F-3). A status a user cannot read is worse than a column 32px off.
- **D-4 — the error state has no reference.** Built from the design's own vocabulary: the analyzing card's geometry with a danger border and the danger icon tile from the excluded-card treatment.
- **D-5 — no hover or active styling anywhere in this feature.** The project's convention is inline style objects (SourcePanel 39, DestinationPanel 36), which cannot express pseudo-classes. Matching that convention means matching its limitation. Flagged for the team rather than resolved unilaterally, since fixing it properly means introducing a stylesheet or a hover-state hook and that is a project-wide convention decision, not this feature's call.
- **D-6 — the bulk button's colour is state-driven, and it reads oddly.** Transcribed from the design: with exclusions present the button is danger-red and reads `Include everything`; with none it is neutral and reads `Exclude all flagged`. So red lands on the *restorative* action and neutral on the *destructive* one. Defensible as "red signals you currently have exclusions", but a red-outlined button is normally read as a warning about the action, not the state. **Left as designed and flagged for design review** — inverting it silently would be redesigning, not pixel-matching.

## Phase 3b — the duplicate footer, and the data-loss bug behind it

Raised by the user against a running build: *"why have you put an extra Continue to Destination … we already have one in the footer?"* They were right, and the duplicate turned out to be the visible symptom of a silent data-loss bug.

### What was wrong

`WizardChrome` owns the footer. A panel's contract — stated in its own docblock — is to *publish a gate*, not to draw a footer: `DestinationPanel` does exactly that with one `useRegisterStepGate` call. `AuditPanel` instead grew a private `AuditFooter` **and never registered a gate**, so:

| Button | Path | Saved? |
|---|---|---|
| The panel's own footer | `onProceed` → `dispatch(proceedFromAudit)` | ✅ |
| The chrome footer (the one that looks official) | `runAdvance` → no gate → falls through to `OPEN_GATE` → `onAdvanced()` | ❌ **navigated only** |

So the two buttons did different things, and **the one a user would naturally click advanced to Content mapping without persisting a single exclusion** — defeating the entire purpose of the step. Confirmed against the live store: `database-v3/projects.json` held saved decisions for **1 of 8 projects**, and that one record contains a lone `itemOverrides` entry with empty `categories` — one row checkbox, no card switch.

The status-line disagreement visible in the screenshot (`Audit complete — 1 excluded, 71 will migrate` above, `Generating audit…` below) had the same single cause: `WizardChrome` builds `stepContext` from the *persisted project*, so `auditReady` / `excludedCount` / `migratingCount` were never populated and the resolver always took its `!auditReady` branch.

### The fix

1. **`AuditPanel`** — `AuditFooter` and its three call sites deleted, along with the now-dead `footerBar` and `primaryAction` styles. Replaced by one `useRegisterStepGate({ satisfied: ready && !saving, blockedReason, advance, statusLine })`. `advance` resolves `false` on a failed persist, which is what stops the chrome navigating; the panel renders the failure itself as a `role="alert"` line, since the chrome has no channel for a step's own error.
2. **`StepGate`** — new optional `statusLine?: string`. Deliberately the finished **string**, not a context object: `useRegisterStepGate` re-registers off a dependency list of primitives, and an object literal would change identity every render and loop. Panels still resolve it through `statusLineFor`, so the copy keeps coming from the shared step definition (TC_AR_132 holds).
3. **`WizardFooter`** — prefers `gate.statusLine` over its own, and now renders the blocked reason as **visible text** as well as keeping it on the action's `title`. TC_AR_128 requires it findable by `getByText`; TC_MWC_035/036 pin the `title`. Both hold, and a tooltip was the wrong sole home for it anyway — it never appears for keyboard or touch users, and a `title` on a *disabled* button is not reliably announced.

### The test lesson — a footer test that never mounted the footer

All 20 tests in `AuditFooterGate.test.tsx` passed throughout, because `renderPanel` mounted `AuditPanel` **alone** and asserted against the footer the panel drew itself. A test that does not mount the component under test cannot see it misbehave.

`renderPanel` now mounts the real composition — panel + real `WizardFooter` inside a real `StepGateProvider`. **Every existing assertion was left untouched**; they query by role and accessible name, so they did not care which component rendered the button. Two were *strengthened*, not relaxed:

- **TC_AR_133 (positive)** is named *"persists the decisions **and then advances**"* but only ever asserted the persist. That missing half is precisely how the bug survived. It now asserts `onAdvanced` fired.
- **TC_AR_134 (negative)** now asserts the wizard did **not** advance on a failed save — the half that matters, since advancing past a failed save is the data loss itself.

Verified non-vacuous by disabling the gate registration and re-running: **13 of 20 fail**, including TC_AR_133 (positive) and TC_AR_110. Under the old panel code the retargeted composition also fails outright — two buttons share one accessible name, so `getByRole` throws on ambiguity.

Confirmed in a real (effect-running) render:

```
[analyzing] footer="Back | Generating audit — you can continue once it finishes | Finish the audit to continue | Continue to Destination"  disabled=true   buttons=1
[ready]     footer="Back | Audit complete — 1 excluded, 1,203 will migrate | Continue to Destination"                                      disabled=false  buttons=1
```

`ui` 994/994, `api` 1042/1042, `tsc --noEmit` clean.

### The recurring hazard in this run: weak negatives

Three separate instances, all found and fixed rather than shipped:

1. **`TC_AR_165`** (tranche 2c) — `expect(status).toBeGreaterThanOrEqual(400)` passed against the unimplemented stub's 500. Now asserts **409** plus that no filesystem call was reached.
2. **Four absence assertions** (tranche 3a) — passed against a `null`-rendering component. Now anchored on the state being present first.
3. **Avoided by construction** (tranches 3b and 3c) — every absence assertion scoped inside a `within(getByRole('region'|'group'|'row', …))` lookup that fails first when nothing renders.
4. **`it.each` hid four TC ids from the source** (tranche 3c) — traceable at runtime, invisible to a grep, and it skewed the pairing count. Rewritten explicitly.

The pattern is worth naming for whoever reviews this: **in a green suite a weak negative is indistinguishable from a satisfied one.** The only reliable defence is that a negative must fail for a stated reason before implementation exists, and an assertion that can only ever pass is not a test.

### Decisions surfaced while writing tranche 2a

Writing the resolution tests forced three rules that the spec implies but never states outright. Each is now pinned by a test, and each is worth a glance in case the intended reading differs:

1. **A category state of `include` must resolve identically to no state at all** (`TC_AR_106 (negative)`). Two representations of the same intent exist — `{}` before the user touches anything, and `{unusedAssets: 'include'}` after they exclude then re-include. AC-2.3 requires toggling back to restore the *exact* pre-audit state, which is only true if these resolve the same.
2. **"Exclude all flagged" must clear surviving `include` overrides** (`TC_AR_055b (negative)`). Setting only the two category states leaves earlier per-row inclusions standing, so the button flips its label to "Include everything" while three rows are quietly still included — the impact panel then disagrees with the label the user just pressed. FR-6.12 says "every flagged item", so clearing is the correct reading.
3. **The helpers must not mutate their input** (`TC_AR_116 (negative)`). The client holds the persisted set and the working set side by side to know whether anything is unsaved; in-place mutation makes those the same object and the comparison always false.
