Gaps / Needs Clarification

  • Empty-state after deleting the last project — the source documents specify the list refreshing after a deletion (FR-2.6) but say nothing about what the dashboard shows when the final project is deleted. No test case was written for it rather than guessing at an empty-state behaviour.
  • Folder-removal failure visibility (TQ-2, unresolved) — the API contract states a folder-removal failure returns 200 and is logged, and TC_PL_007 tests that. The same open question asks whether the operator should instead be told that disk was not reclaimed. If that is decided differently, TC_PL_007 and the observability cases change.
  • Concurrent-create window (EC-11 / TQ resolution) — the source documents explicitly accept the check-then-write race rather than engineering against it, and state that no automated test will be written for it. TC_PL_119 is therefore marked Automated = N and exists to record the expectation, not to be scripted. Flagged so the absence is visibly deliberate rather than an oversight.
  • Method for producing the performance fixture — NFR-1 states a 30-second bound for approximately 160 MB across approximately 10,000 files, but no document states how that fixture is to be produced or whether the bound is measured on a specific machine class. TC_PL_074 records the assertion; the measurement setup is unspecified.
  • 'Without a full page reload' (FR-2.6) — the requirement is stated but the documents give no observable definition of what distinguishes a refresh from a reload. TC_PL_055 asserts the project disappears from the list; the no-reload half of the requirement is not independently verifiable from the specification as written.
  • 500 response body shape — the API contract lists a 500 for a failed record write but does not specify the response body or message key, so TC_PL_006 asserts the status only.
  • Delete from inside an opened project (PQ-1 / TQ-4, unresolved) — the documents scope the delete affordance to the dashboard card for this release. No test cases cover a delete entry point elsewhere; if that question resolves in favour of adding one, cases must be added.
  • Surfacing reclaimed bytes in the interface (PQ-3, unresolved) — reclaimed bytes are specified as a log field only. No test asserts any interface display of it, since the documents place that out of scope for this release.
  • Accessibility focus-return target (NFR-3) — the requirement says focus must return to 'a sensible element'. TC_PL_054 asserts focus is not lost to the document body, which is the strongest unambiguous check available; the specific target element is not named in the source.
