Gaps / Needs Clarification

  • EC-6 / Q-13 / TQ-1 — duplicate project names. feature.md EC-6 says the behaviour on a name conflict "depends on whether duplicate names are permitted at all", and trd.md TQ-1 leaves that undecided. No test case can state an expected result for submitting a name that already exists.
  • Q-1 / FR-8.9 — first-run empty state copy and placeholder card treatment. FR-8.3 requires a first-run empty state but specifies none of its text, and FR-8.1 specifies the placeholders' footprint but not their visual treatment. The cases above therefore assert only presence, footprint and behaviour — not copy. Once copy is signed off, the corresponding cases need a literal-string assertion added.
  • Q-3 / FR-7.14 — create-project modal design. The requirement is that the modal "follow the existing v3 modals", which is a direction rather than a checkable specification. The single case covering it is necessarily a manual comparison with no pass/fail threshold.
  • Q-15 — project card hover state. The design declares a transition on the card's border colour, shadow and transform but specifies no hover values. No test case can assert what the card should look like on hover.
  • Q-16 / FR-1.1 — the top bar's substitute for the organization block. The design's top bar is built around an organization block this revision removes. FR-1.1 substitutes the product name, but that is a drafted deviation, not a specified design, so the only case covering it is a manual design review.
  • Q-4 — no Failed status. FR-5.5 defines a Completed badge, and prd.md PR-1 acknowledges that a migration can fail, but no requirement defines a Failed badge, its text or its derivation. No case exists for a failed project.
  • FR-5.5 — Completed is unreachable end-to-end. The requirement states that no project can currently reach this state because v3 has no migration-completion signal. The case above therefore exercises the derivation directly with a completed input; it verifies the derivation rather than the user-visible outcome.
  • FR-4.9 / Q-2 — resume step for steps that persist nothing. The resume step is derived from the persisted source and destination only. No requirement states what should happen for a user who reached Content mapping, Preview, Migrate or Verify without persisting anything. Cases exist only for the three derivable conditions.
  • Q-10 / EC-15 / TQ-5 — pagination threshold. "All projects rendered, no pagination" is testable and is covered, but the project count at which that becomes unacceptable is explicitly undefined, so no threshold case exists.
  • Q-12 / NFR-8 — supported browsers. NFR-8 requires correct rendering in "the browsers already supported by the v3 UI" and marks the exact versions TBD. The compatibility case above cannot name the browsers it should be run against.
  • TQ-2 — server-side create idempotency. trd.md states API-2 is deliberately not idempotent, so two identical requests create two projects, while also recording as open whether an idempotency key should exist. The concurrency case above covers only the client-side guard.
  • TQ-3 — user identity caching. Whether the user endpoint is called on every page mount or cached for the session is undecided. This changes the expected request count, so the request-count case above deliberately covers only the project list request.
  • TQ-4 / NFR-1 — how the 100 ms bar is measured. trd.md records that a wall-clock assertion for this threshold is unreliable in continuous integration and leaves the measurement approach open. The performance case above is therefore marked as not automated.
  • FR-3.5 — responsive grid has no stated breakpoints. The requirement is that the grid reflows "without a horizontal scrollbar appearing on the page body", but no breakpoint set and no minimum supported width are specified, so the case cannot enumerate the widths to test and is marked manual.
  • FR-1.6 — "not the wizard chrome's app bar component" is architectural. It constrains how the page is built rather than what it does, and the two bars now show the same product name. The case above tests it only indirectly, by asserting the projects bar carries an avatar and no step-position or source indicator.
  • Q-6 — nothing sets the soft-delete marker. FR-9.5 requires the marker and its exclusion from listings, but no delete action exists anywhere in the product. The exclusion cases above can only be exercised by placing an already-marked record in the store directly, never through a user action.
  • PQ-3 — description is collected and displayed nowhere. The create modal collects a description and the record stores it, but no requirement states where it is ever shown. No display case exists for it.
  • PQ-5 — irreversibility warning in the create modal. prd.md records as undecided whether the create modal should warn that a project cannot be deleted. No case asserts the presence or absence of such a warning.
  • FR-9.13 — the former paths' 404 depends on nothing else re-registering them. The endpoint-path case asserts the old /v3/org/:orgId/... paths no longer resolve, which is a check against a stale mount. It cannot detect a future feature legitimately reintroducing an organization-scoped route for a different purpose.
